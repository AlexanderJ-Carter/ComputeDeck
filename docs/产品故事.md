# 产品故事

## 一句话

ComputeDeck 把一组分散的算力节点收进一个控制面：节点、任务、模型、入口都能看见，也能交给 Agent 操作。

## 为什么叫 Deck

Deck 可以理解成一层层叠起来的甲板。一个集群本来就有好几层：

- 机器和 GPU 是最底下的一层；
- 任务、队列和租约叠在上面；
- 模型、工具栈是任务要用的资源；
- 推理入口、远程接入是对外的门。

这些层以前散在群聊、终端、各自的脚本和几个不同工具里。ComputeDeck 把它们叠到同一张控制面上，所以叫 ComputeDeck。

Logo 里的三层就是这三类东西：算力层、任务层、入口层。右侧连线的三个节点表示每一层都接着具体机器，橙色点是控制节点。

## 从哪来

最早要解决的问题很具体：实验室里有一批能 SSH 的 GPU 机器，卡谁在用靠群聊，任务怎么启停靠各自脚本，入口通不通靠记忆。想知道一台机器能不能腾空，要开好几个终端。

后来发现，难的其实不是“看 GPU”，而是几件事之间没有共同的状态：

- 谁能占卡、占多久，没有记录；
- 任务装在哪、怎么启停，每个业务一套；
- 模型文件在哪、训练栈和推理栈装没装，靠人记；
- 对外入口和内部节点是什么关系，排查时说不清；
- Agent 想帮忙，却没有稳定的 HTTP / MCP 契约。

ComputeDeck 就是把这些状态收在一起，让网页、命令行和 Agent 读写同一份东西。

## 现在管什么

- 节点：在线、GPU 占用、隔离、探活、终端；
- 任务：Job 模板、启停、排队、租约、watchdog；
- 资源：模型文件、训练栈、推理栈；
- 入口：Edge、LiteLLM、nginx、TLS、远程接入；
- 协作：看板、公告、小助手、MCP 工具。

GPU 调度是其中一项能力，不是产品的全部。节点、任务、模型和入口都在同一个控制面里，这是 ComputeDeck 和“一个 GPU 看板”的区别。

## 亮点

不靠形容词，靠能测的东西：

- **节点不装 agent**：控制面通过 SSH / Ansible 操作工作节点，节点上不常驻第二个控制进程。加机器不需要先装一套运行时。
- **控制面自身很轻**：本机回环下 `/api/health` p50 约 0.8ms，`/api/overview?light=1` p50 约 3.5ms；8 并发健康检查约 1,600–1,740 req/s。数据和方法见 [性能与基准](性能与基准.md)。
- **首屏更小**：`app.js` 从 321KB 压到 83KB（74%），`style.css` 从 149KB 压到 27KB（82%）。
- **同一份状态**：网页、CLI、MCP 读写同一套 state，不需要为每个入口再维护一份列表。
- **只有一层节点 LB**：LiteLLM 或 Edge 二选一，避免 nginx / Edge / LiteLLM 对同一批节点重复负载均衡。
- **配置能落地**：nginx 片段可校验、可 reload、失败回滚，`doctor` 会指出漂移；不是生成完让用户自己猜。
- **Agent 可控**：写操作先确认，工具分级；不是把 shell 直接交给模型。

## 边界

ComputeDeck 不替代这些：

- 不做虚拟化或容器编排平台；
- 不做训练框架，也不重写 LLaMA-Factory / DeepSpeed / Ray / vLLM；
- 不替代 LiteLLM 的虚拟密钥、预算和审计；
- 不把被控节点拉进 OIDC，工作节点只走 SSH。

它负责的是控制面：发现、状态、配置、调度入口，以及把这些能力稳定地交给人和 Agent。

## 名字和命令

- 产品名：**ComputeDeck**
- 命令行 / MCP 服务名：`gpu-control`
- 仓库和镜像：`ComputeDeck` / `computedeck`

改名不改变 CLI，现有脚本和 Agent 配置可以继续用。

## 宣传用短文案

**一句话**

> 一台主控，管住一组算力节点：节点、任务、模型和入口都在同一张控制面上。

**三句话**

> ComputeDeck 是一套多节点算力控制面。网页、命令行和 Agent 读写同一份状态；节点、任务、模型、入口不用再分散在群聊和各自的脚本里。

**适合谁**

- 手里有一批 SSH 机器、需要统一看占用和启停任务的团队；
- 同时跑训练、推理和常驻服务，入口和节点关系容易乱的环境；
- 想让 Cursor / Claude 等 Agent 安全地参与运维，但需要确认和审计的团队；
- 希望配置跟着仓库走，换一批机器主要改配置的场景。

**不适合谁**

- 只需要单机 `nvidia-smi` 的个人；
- 需要完整 Kubernetes 调度、隔离和多租户的平台；
- 想用控制面替代训练框架或模型服务本身的团队。
