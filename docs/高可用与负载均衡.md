# 高可用、保活与负载均衡

ComputeDeck 的高可用分三层：推理入口（LiteLLM / Edge）、Job 保活（watchdog）、控制面进程（systemd）。  
默认路径：LiteLLM 直连节点做唯一 LB，Edge / nginx 只做 18080 前置；启用默认 Job 的 watchdog 自动保活。

## 0. strategy 字段说明

| 字段 / 参数 | 作用域 | 含义 |
|-------------|--------|------|
| `cluster.strategy` | 集群标签 | 场景说明（如 `inference-pool`），**不**驱动 LB 算法 |
| `gateway.ingress.strategy` | Edge / nginx 前置（无 LiteLLM 时才是节点 LB） | `round_robin`（默认）/ `least_conn`（按在途连接） |
| LiteLLM `routing_strategy` | 唯一节点 LB | `least-busy` / `simple-shuffle` / 延迟路由等（见 LiteLLM 文档） |
| `GET /api/endpoints/lb?strategy=` | 客户端片段 | 给调用方的选路建议（如 `least_latency`），**不是** Edge 配置 |

改节点负载算法：改 `gateway.routing_strategy` 后重新生成 LiteLLM model_list；只在无 LiteLLM 的部署里改 `gateway.ingress.strategy`。

## 1. 推理入口与负载均衡（LiteLLM）

![推理入口：客户端 → LiteLLM → 健康端点池，18080 可选前置](assets/edge-ingress.svg)

LiteLLM 是唯一节点 LB：

- model_list 为每个节点端口生成一个 deployment；`routing_strategy` 选健康节点；
- `num_retries` / `allowed_fails` / `cooldown_time` 由 LiteLLM router 负责；
- 18080 的 Edge / nginx 只做 TLS/域名/网页，单 upstream 指向 `127.0.0.1:4000`；
- 模型名、虚拟密钥、预算、Admin 都在 LiteLLM。

相关配置（`cluster.gateway`）：

```json
{
  "litellm_upstream": "nodes",
  "routing_strategy": "least-busy",
  "openai_proxy_port": 4000,
  "ingress": {
    "port": 18080,
    "proxy_to": "http://127.0.0.1:4000"
  }
}
```

查看/运维：

```bash
gpu-control gateway status
gpu-control gateway render
gpu-control gateway start --kind litellm
gpu-control endpoints --refresh
```

## 2. 轻量部署：Edge 做节点 LB

不使用 LiteLLM 时，内置 Edge 直接从 `state/endpoint_health.json` 选健康上游：

- 支持 `round_robin` / `least_conn`、连接失败重试、失败冷却；
- `ingress.proxy_to` 留空，`litellm_upstream` 可设为 `edge` 以便 LiteLLM 只做治理层；
- 健康入口：`/_gpu_control/health`。

```bash
gpu-control gateway ensure          # 渲染产物 + 拉起配置的主入口
```

### 2.1 nginx 作为节点 LB 时自动跟随

用 nginx 替代 Edge 时，节点增减或健康状态变化不会自动进入 nginx 的静态 upstream。配置 `gateway.nginx.apply_path` 后，可以让控制面负责重渲染和 reload：

```bash
gpu-control gateway nginx --apply
gpu-control gateway nginx --watch --background
```

`--watch` 只在渲染结果变化时执行 `nginx -t` 和 reload；校验失败会回滚。状态见 `gpu-control gateway status` 的 `nginx.in_sync` / `nginx.last_sync`。

多台 nginx 节点共用一个配置文件时，控制面机器正常 `--watch`，其余节点用 `--watch --reload-only` 只跟随文件变化并 reload。

## 3. Job 保活（watchdog）

watchdog 定期对 Job 执行 `status`，不健康时 `restart` + `wait`：

```json
"watchdog": {
  "enabled": true,
  "jobs": [],
  "interval_sec": 60,
  "max_restarts": 3,
  "failure_threshold": 2,
  "nodes": "all"
}
```

- `jobs` 为空时使用 `default_job`；
- 默认**连续 2 次**不健康才重启，避免一次网络抖动就重启线上服务；
- 健康检查成功会**清零**重启计数，后续故障仍有完整预算；
- 被隔离节点会被跳过；
- 状态：`state/watchdog.pid`、`state/watchdog_state.json`、`state/watchdog.log`；看板「自动重启」行。

```bash
gpu-control watchdog --background
gpu-control watchdog --job sft --interval 30 --once   # 单轮检查
systemctl status gpu-control-watchdog                  # 生产建议 systemd
```

> watchdog 只负责“进程/服务活着”；训练是否收敛、推理是否可服务要看 Job 自己的 `wait` 契约
> （`vllm-serve` 会做 HTTP/TCP 就绪检查）。

## 4. 控制面进程保活

生产建议用 systemd（见[生产部署](生产部署.md)）：

```ini
Restart=on-failure
RestartSec=3
```

UI 支持 SIGTERM 优雅退出并清理 pid；Edge/LiteLLM 的 pid 文件由 gateway 管理。
控制面按单活跃实例部署；多机入口用反向代理或主备切换，同一时间只让一个实例执行编排动作。

## 5. 故障转移边界

| 场景 | 行为 |
|------|------|
| 单个推理端点失败 | Edge 重试其它健康上游；失败上游冷却 |
| 整个节点不可用 | 健康探测剔除；watchdog 尝试重启 Job |
| Job 崩溃 | watchdog 按 `max_restarts` 重启并等待 |
| Control 的 Edge 进程退出 | systemd 重启；`gateway ensure` 可恢复 |
| Control 主控宕机 | 用外部主备或反代接管入口；编排动作仍由活跃实例执行 |

## 6. 默认配置建议

```json
{
  "gateway": {
    "ingress": {
      "enabled": true,
      "kind": "edge",
      "strategy": "round_robin",
      "retries": 2,
      "cooldown_sec": 30
    }
  },
  "watchdog": { "enabled": true, "jobs": [], "interval_sec": 60, "max_restarts": 3, "failure_threshold": 2 }
}
```

这样新集群默认就有：单入口、健康感知 LB、请求级失败换上游、Job 自动重启；AI Gateway 在就绪时自动挂上。
