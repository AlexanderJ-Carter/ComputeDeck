# 打包与发布

ComputeDeck 的交付物只有四类：**源码包**、**控制面镜像**、**VS Code 扩展（VSIX）**、**文档站**。  
仓库即控制面，**不发 PyPI / npm**；正式版本以 GHCR 镜像 + GitHub Release 为准。

> **为什么不做 npm？** VS Code / Cursor 扩展的标准分发单元是 **VSIX**（Marketplace / Open VSX / 内网 `code --install-extension`），不是 npm 包。控制面是仓库/镜像，也不是前端库。若以后要「一键安装扩展」，优先 Open VSX 或 Release 附件，而不是 `@computedeck/vscode` 这种 npm 名。

## 0. 一张图

```
VERSION / pyproject / package.json / CHANGELOG
                    │
         scripts/release_notes.py --check
                    │
        ┌───────────┼────────────┬─────────────┐
        ▼           ▼            ▼             ▼
   源码 tar.gz   控制面镜像     VSIX        文档站
   （git archive）（GHCR）   （vsce）     （MkDocs）
        └───────────┴────────────┴─────────────┘
                    │
              SHA256SUMS
```

## 1. 版本一致性

四个文件必须一致，CI 与本地脚本都会校验：

| 文件 | 字段 |
|---|---|
| `VERSION` | 纯版本号，如 `1.2.6` |
| `pyproject.toml` | `project.version` |
| `extensions/vscode/package.json` | `version` |
| `CHANGELOG.md` | 存在 `## [<version>]` 段落 |

```bash
python scripts/release_notes.py --check 1.2.6
```

准备下一个版本（不推送）：

```bash
python scripts/prepare_release.py --bump patch --apply --check
```

## 2. 本地一键打包

```bash
./scripts/package_all.sh                 # 校验 + 源码包 + VSIX + 文档 + 镜像 + 校验和
./scripts/package_all.sh --no-image      # 只打包源码 / VSIX / 文档
./scripts/package_all.sh --skip-check    # 跳过 check.sh（不建议）
./scripts/package_all.sh --push          # buildx 多架构推 GHCR（先 docker login ghcr.io）
```

产物在 `dist/<version>/`（已忽略提交）：

```text
dist/1.2.6/
├── computedeck-1.2.6.tar.gz            # 源码包（git archive HEAD）
├── computedeck-vscode-<扩展版本>.vsix  # VS Code 扩展
├── help/                               # MkDocs 文档站（可选）
├── manifest.json                       # 产品版本 / 扩展版本 / commit / 构建时间
├── SHA256SUMS
└── ...
```

> 源码包取 **HEAD**。工作区有未提交改动时脚本会警告；要包含改动请先提交。
>
> 本地开发时扩展版本可以独立于产品版本（例如产品 1.2.7、扩展 1.2.29）；`manifest.json` 会分别记录。发版前 `prepare_release` 会把两处收束到同一版本。

打包结束会自动跑：

```bash
python scripts/verify_release.py dist/1.2.6
```

它检查 `SHA256SUMS` 是否与实际文件一致、`manifest.json` 是否齐全，并回显版本和 commit。手工交付镜像 / 源码包前建议也跑一次。

## 3. 源码包

```bash
git archive --format=tar.gz --prefix="computedeck-1.2.6/" \
  -o dist/computedeck-1.2.6.tar.gz HEAD
```

解压后按 README「快速开始」安装；`config/local/`、`state/`、`deploy/ssh/` 等本机配置不会进入包内。

## 4. 控制面镜像

### 4.1 本地构建

```bash
docker buildx build --load \
  --build-arg VERSION=1.2.6 \
  --build-arg VCS_REF="$(git rev-parse HEAD)" \
  --build-arg BUILD_DATE="$(date -u +%Y-%m-%dT%H:%M:%SZ)" \
  -t ghcr.io/alexanderj-carter/computedeck:1.2.6 \
  -t computedeck:1.2.6 .
```

或直接 `./scripts/package_all.sh`。Compose 用法：

```bash
cp -n .env.example .env
COMPUTEDECK_IMAGE=ghcr.io/alexanderj-carter/computedeck:1.2.6 docker compose up -d
```

镜像内已包含 Web / CLI / MCP 依赖与文档站（`/help/`）；GPU 节点仍是真实主机，不进镜像。

### 4.2 正式发布

推送 `v*` tag 后由 `.github/workflows/release.yml` 自动完成：

1. 校验版本与 `check.sh`、构建 MkDocs；
2. 用 CHANGELOG 建 GitHub Release；
3. 构建并推送镜像到 `ghcr.io/<owner>/computedeck`，附 OCI 标签、SBOM 与 provenance；
4. 打包 VSIX 与源码包（含 SHA256），附加到 Release。

镜像标签策略：

| 版本 | 标签 |
|---|---|
| 正式版 `1.2.6` | `1.2.6` · `1.2` · `latest` |
| 预发布 `1.3.0-beta.1` | 仅 `1.3.0-beta.1` |

```bash
docker pull ghcr.io/alexanderj-carter/computedeck:1.2.6
```

> fork / 新 Package 首次推送后若匿名拉取 401：Packages → 设置 → Public。

## 5. VS Code 扩展（VSIX）

```bash
./scripts/package_extension.sh          # 只打 VSIX
code --install-extension extensions/vscode/computedeck-vscode-*.vsix
```

- `extensions/vscode/**` 变更时 `.github/workflows/vscode.yml` 自动打包并上传 artifact；
- 打 tag 时由 release.yml 附加到 GitHub Release；
- 扩展版本与主版本同步，`release_notes.py --check` 会校验。

扩展内置 5 步上手指南（自定义 Webview，命令「ComputeDeck: 五分钟上手」）；不再使用原生 Walkthrough，避免编辑器默认排版把步骤堆成蓝色按钮。

### 5.1 发布渠道

| 渠道 | 适用 | 现状 |
|------|------|------|
| **GitHub Release 附件（VSIX）** | 手动下载、内网分发、离线安装 | 已在 release.yml 中产出 |
| **Open VSX** | Cursor、Windsurf、VSCodium、CodeLab 等 | 命名空间 `computedeck` 尚未注册，工作流已备好 |
| **VS Code Marketplace** | 官方 VS Code 用户 | 未发布；需要 Microsoft 发布者账号 |
| **npm** | — | 不使用。VS Code 扩展的分发单元是 VSIX，不是 npm 包 |
| **PyPI** | — | 暂不发布，原因见下 |

Open VSX 发布步骤：

1. 在 <https://open-vsx.org> 用 GitHub 登录，关联 Eclipse 账号并同意 Publisher Agreement；
2. 在 Settings → Access Tokens 生成 Token，写入仓库 Secret `OVSX_PAT`；
3. 创建命名空间：`npx ovsx@1.4.0 create-namespace computedeck -p "$OVSX_PAT"`；
4. 在 GitHub Actions 手动运行 `Publish VS Code extension`，输入 `publish`。

本地也可以直接发：

```bash
npx --yes ovsx@1.4.0 publish extensions/vscode/computedeck-vscode-<version>.vsix -p "$OVSX_PAT"
```

VS Code Marketplace 需要先注册发布者，并通过 Azure DevOps 或 Trusted Publishing 鉴权。注意 Azure DevOps 的全局 PAT 将在 2026-12-01 停用，新接入应直接使用 `vsce publish --oidc`；否则就继续用 VSIX / Open VSX。

### 5.2 为什么暂不发布 PyPI

`pyproject.toml` 目前只描述依赖，设置了 `[tool.uv] package = false`，直接 `uv build` 会因 setuptools 无法自动发现包而失败。控制面不是一个可独立安装的 Python 包：它还需要 `lib/`、`bin/`、`web/`、`playbooks/`、`jobs/` 和 `config/examples/` 一起工作，`bin/gpu-control` 也按仓库目录查找资源。

另外，PyPI 上的 `gpu-control` 已被一个无关的 NVIDIA 风扇控制项目占用。如果要发布，发行名需要用 `computedeck`，入口命令仍是 `gpu-control`，并且要先完成：

- 定义包布局与包数据（静态资源、playbook、示例配置）；
- 把路径解析从“仓库相对路径”改成“安装数据目录 / 当前工作目录”；
- 处理升级时的 `config/local/` 和 `state/` 迁移。

在这些完成前，源码包 + 容器镜像 + 仓库即控制面的方式更可靠。

### 5.3 npm 为什么不需要

本项目没有需要作为 npm 包分发的 JavaScript 运行时代码。扩展本身由 VS Code、Cursor 等编辑器加载，安装单位是 VSIX；CLI 和 MCP 是 Python，分别从仓库或容器运行。把扩展发到 npm 既不能让编辑器直接安装，也会多一套版本和供应链维护成本。

## 6. 文档站

```bash
uv pip install -r requirements-docs.txt
mkdocs build --strict          # 产物 web/static/help/
```

镜像构建时会把文档站拷进 `/app/web/static/help`；UI 的「帮助」入口与 `/help/` 直接可用。

## 7. 发布流程

```bash
# 1) 准备版本与 CHANGELOG
python scripts/prepare_release.py --bump patch --apply --check

# 2) 本地验收（可选）
./scripts/package_all.sh

# 3) 提交并打 tag
git add -A && git commit -m "chore: release 1.2.6"
git tag -a v1.2.6 -m "ComputeDeck v1.2.6"
git push origin main --tags
```

随后在 GitHub Actions 观察 `Release` 工作流；完成后检查：

- GitHub Release 正文与附件（VSIX）；
- `ghcr.io/<owner>/computedeck:<version>` 可拉取；
- 文档站与 `/help/` 可打开；
- `GET /api/health` 与 `GET /api` 正常。

## 8. 常见问题

**`git archive` 报 `fatal: not a git repository`**  
`package_all.sh` 必须在仓库根目录的 git 工作树中运行。

**VSIX 打包提示 repository 缺失**  
脚本已带 `--allow-missing-repository`；不要手工去掉。

**镜像健康检查失败**  
容器内监听 `0.0.0.0:8787`；检查端口映射与 `GPU_CONTROL_UI_HOST`，首次启动有 15s start-period。

**文档构建 warning**  
`mkdocs build --strict` 会把 warning 当错误；本地预览可先用 `mkdocs serve` 排查。
