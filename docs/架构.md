# 架构定位

## 一句话

**gpu-control = 通用多节点 GPU 控制面**（SSH + Ansible fan-out）。  
模型推理、训练脚本、临时实验都是其上的 **Job / 可选模块**，不是产品唯一目标。

## 为什么不是「只做模型部署」

| 诉求 | 落点 |
|------|------|
| 看卡、腾空、隔离、远程命令 | **核心**（与模型无关） |
| 登记占用、防抢占 | **核心** lease / cordon |
| 启停任意脚本 | **核心** `jobs/*.json` |
| 推理池 / API 健康 / 一键部署 | **可选模块**：推理工作负载 |
| 模型权重下载 / 缓存检查 | **可选模块**：模型工具 |

若做成纯模型平台，会绑死 HF/SGLang 流程，反而削弱「小集群控制台」价值。  
若完全不做模型便利，日常推理运维又要手搓命令。因此采用 **Core + Modules**。

## 分层

```text
┌─────────────────────────────────────────┐
│  Web / CLI（同一控制面）                  │
├─────────────────────────────────────────┤
│  Core                                   │
│  节点 · GPU 快照 · exec · lease/cordon  │
│  doctor · 连通质量 · 配置向导            │
├─────────────────────────────────────────┤
│  Workloads（jobs/*.json）               │
│  任意 start/stop/status 脚本             │
├─────────────────────────────────────────┤
│  Modules（可选）                         │
│  · inference：endpoints / health / deploy│
│  · models：缓存检查 / 拉取权重           │
└─────────────────────────────────────────┘
```

## 工程能力：终端 / 指标 / 负载

| 能力 | 设计 | 实现 |
|------|------|------|
| **交互终端** | 页面内等同 SSH 进节点（真 PTY，可跑 vim/top） | WebSocket `/ws/terminal` + paramiko `invoke_shell` + xterm.js |
| **批量输出** | 「命令 / 一键运维」结果区，不是交互 shell | `/api/exec` 结构化 stdout |
| **主机指标** | CPU%%、load、内存 | `gpu-control metrics` → `state/host_metrics.json`，总览/终端页展示 |
| **推理负载** | 控制面不代理流量；给出健康×延迟排序的客户端轮询列表 | `/api/endpoints/lb` |

原则：控制面做 **编排与可观测**；请求面负载均衡留在客户端 / 上游网关，避免把控制面做成数据面瓶颈。

## 刻意不做

- 完整 K8s / Slurm 替代  
- 默认上 Ray / NCCL 训练编排  
- 公网鉴权与多租户计费（内网控制面）  
- 在控制面反向代理推理流量（LB 只给建议列表）

## 与 K8s 概念对照（心智模型）

| 概念 | 本项目 |
|------|--------|
| Node | `nodes.json` 中的 GPU 机 |
| Job | `jobs/<name>.json` + 远端脚本 |
| kubectl | `gpu-control` CLI |
| Dashboard | `gpu-control ui` |
| Cordon | `free --cordon` / `node uncordon` |
